# security-audit：代码安全审查

只做检查和汇报，**不自动改代码**。查完按风险等级输出一份「风险清单」，每一条都有「文件:行号 + 问题 + 为什么危险（人话）+ 建议怎么改」。

## 检查范围

- 默认检查**当前改动的文件**和项目里的**配置文件**；用户指定文件/目录时，只查指定范围。
- 用 `git diff` / `git diff HEAD` 定位改动；配置文件包括 `.env*`、`.env.example`、`requirements.txt`、`package.json`、`pytest.ini`、`*.config.*`、`settings.json` 等。

## 四大检查项

### 1. 敏感信息泄露（代码里写死的密码/密钥）

在代码里找「写死的秘密」，常见形态：

- 变量名带 `password` / `secret` / `token` / `key` / `apiKey` / `apiSecret` / `privateKey` / `accessKey` 等，而它的值是一串具体的字符串；
- 百炼密钥（`DASHSCOPE_API_KEY`）、JWT 签名密钥、数据库连接串等。

判定原则：

- 🔴 **前端（frontend/src/）代码里出现的任何真实密钥/密码**都要报——前端代码会随着网站一起发给浏览器，别人能直接看到。
- 后端（backend/）里的硬编码密钥也要报，但风险通常略低一档。
- 正解是放进 `backend/.env`（已被 .gitignore 排除、不入库），代码里用 `settings.xxx` 读取。

### 2. 注入类漏洞

检查「用户输入直接拼进能执行的东西」：

- **SQL 注入**：把用户输入拼进 SQL 字符串，例如 `f"SELECT * FROM t WHERE id = {id}"`、或 `"SELECT ... WHERE name='" + name + "'"`。正确做法是用 SQLAlchemy 的查询构造器（`db.query(Model).filter(...)`）或参数占位符（`db.execute(text("... WHERE name = :name"), {"name": name})`），让驱动帮你「安全转义」。
- **命令注入**：Python 里 `os.system` / `subprocess.run(..., shell=True)` 拼接用户输入，等于给用户开了一扇执行任意命令的门。
- **路径穿越**：用用户输入拼文件路径（上传的文件名、doc_id、编号等），可能被 `../` 跳出目录、读到不该读的文件。

判定：凡是「用户的输入能以某种方式影响执行的代码/命令/路径/SQL」的，都要报。

### 3. 配置文件里的明文敏感信息

- `.env`、配置文件里明文写的密钥/密码/连接串。
- 还要检查：这些含秘密的文件**有没有被提交进 git**——重点确认 `backend/.env` 被 `.gitignore` 排除、且从没被提交过历史。

### 4. 其它隐患（我认为该提的）

- Python 用 `eval` / `exec` / `pickle.loads` 解析不可信输入；
- 用 `random` 模块生成验证码、令牌等安全相关的东西（应改用加密安全的 `secrets` 模块）；
- 用弱算法存密码（MD5 / SHA1 直接存密码）；本项目应坚持用 bcrypt；
- JWT 相关：密钥太弱、密钥写死在前端、校验不严、过期时间设置不合理；
- 越权：前端传来的 `id`、`user_id` 等没校验归属就用，普通用户能访问 admin 接口；
- 依赖里的已知漏洞（前端 `npm audit`；后端 `pip-audit` 或 `pip list --outdated`）。

## 汇报格式

按危险程度从高到低排，每条一行：

| 文件:行号 | 等级 | 属于哪类 | 问题 | 为什么危险 | 建议 |

等级分三档：

- 🔴 **高危**：能直接利用、或直接把秘密泄露出去
- 🟡 **中危**：有风险但需要一定条件
- 🟢 **低危 / 建议**：潜在隐患，建议顺手改

最后给一句简短总结：整体安全状况如何、最该先修哪几处。

## 注意事项

- **只检查和汇报，不直接改代码**。等用户说「帮我改」之后，再动手修。
- 没证据别乱报；不确定的标「待确认」，说明为什么怀疑。
- 汇报给用户时**用通俗语言**解释「为什么危险」（用生活比喻），别甩术语。
- 这是**防御性检查**，目的是帮作者发现自己代码里的问题并修好，不是用来攻击别人。

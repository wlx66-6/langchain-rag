# ADR-0004：用 SSE 做流式回答，并处理断开、失败与脱敏

- **状态**：已接受
- **日期**：2026-10（改造时补记）

## 背景

大模型逐字生成，若等全文生成完再一次性返回，用户要盯着空白页等好几秒。
需要「边生成边显示」。可选方案：WebSocket、SSE、HTTP 轮询。

## 决策

用 **SSE（Server-Sent Events）** 实现流式输出，并配套三条健壮性规则：

1. **客户端断开检测**：后端在生成过程中检查连接是否已断开（`Request.is_disconnected()`）
   并捕获 `CancelledError`，及时停止生成，不让无用的算力白跑。
2. **失败兜底落库**：生成中途失败时，**依然写入一条兜底的助手消息**，
   保证「用户消息 / 助手消息」成对存在，不在会话里留下悬空的半截记录。
3. **错误脱敏**：发生异常时，**对外的 SSE 事件只给统一文案 + 错误码 `code`**，
   真实的异常堆栈只写进服务端日志——避免把文件路径、依赖版本、甚至密钥片段吐给前端。

前端侧对应地：把 SSE 生命周期抽成 `lib/sse.ts`，用 `AbortController` 管理，
切换会话或组件卸载时**中止在途请求**，并丢弃过期回调，避免旧流的 token 污染新会话。

## 理由

1. **SSE 比 WebSocket 更适合这个场景**：数据流是**单向**的（服务端 → 浏览器），
   SSE 基于普通 HTTP、无需握手协商、天然支持断线重连语义，实现与调试都更简单；
   WebSocket 的双向能力在这里用不上。
2. **断开检测是成本问题**：用户切走页面后仍在生成，等于替一个不存在的听众烧钱烧算力。
3. **失败兜底是数据一致性问题**：会话历史出现「有问无答」的悬空记录，会让用户以为系统坏了。
4. **脱敏是安全问题**：异常文本经常包含绝对路径与内部细节，属于信息泄露面。

## 后果

- 优点：首字延迟大幅下降（用户提问后几乎立刻开始出字）、成本可控、会话记录始终成对。
- 代价：SSE 事件协议与前端解析需保持一致（改动其一要同步另一侧）；测试需要构造流式响应
  （前端用 `ReadableStream` 模拟，后端用 TestClient 逐事件断言）。

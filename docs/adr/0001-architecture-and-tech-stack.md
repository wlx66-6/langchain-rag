# ADR-0001：分层单体架构与技术选型

- **状态**：已接受
- **日期**：2026-10（改造时补记）

## 背景

项目需要满足三件事：能演示一个完整的 RAG 问答链路、代码结构要经得起面试追问、
部署与运行要足够简单（面向个人开发者，无运维团队）。

## 决策

采用**前后端分离的「分层单体」（modular monolith）**：

- 后端 FastAPI，按职责分层：`routers/`（HTTP 层）→ `services/`（业务/检索/加载）→
  `core/`（鉴权等基础设施）→ `models/`（ORM）→ `schemas/`（出入参校验）；
  `config.py` 集中配置。**不引入领域驱动分模块的微服务拆分。**
- 前端 React 18 + TypeScript + Vite，页面级组件 + `lib/` 工具层，不引组件库/状态管理框架。
- RAG 链路：本地 `bge-m3` 做向量化 → Chroma 检索 → 百炼 `gte-rerank-v2` 重排 →
  阿里云百炼 `qwen-plus` 生成。

## 理由

1. **分层单体匹配项目规模**：RAG 问答系统的复杂度在「检索链编排」而非「服务拆分」；
   拆微服务会引入网络、事务、部署成本，收益为负。
2. **分层让每一层可独立测试**：`services/` 下的纯函数可脱网单测（见 ADR-0005），
   这也是本项目能做到高覆盖率的原因。
3. **本地向量模型**：`bge-m3` 本地推理，无外部向量 API 依赖，离线可跑、边际成本为零；
   代价是首次加载模型较慢（已在 README 中说明）。
4. **不用组件库**：页面数量少（登录/注册/对话/知识库/个人中心），引组件库是负担不是助力。

## 后果

- 优点：结构清晰、可测试、无运维负担、面试时每一层都能讲出「为什么」。
- 代价：所有逻辑集中在一个进程，横向扩展能力有限——**这在本项目的目标场景下不是问题**，
  已在 README 的「局限与展望」中如实说明。
- 相关：ADR-0002（数据库）、ADR-0003（鉴权）、ADR-0004（流式输出）。

# ADR-0002：保留 SQLite 作为关系库，Chroma 作为向量库

- **状态**：已接受
- **日期**：2026-10（改造时补记）

## 背景

系统需要存两类数据：结构化的业务数据（用户、会话、消息、知识文档元信息）与
向量化的文本块。改造前使用 SQLite（业务数据）+ Chroma（向量），曾被考虑迁到 PostgreSQL + pgvector。

## 决策

**保留 SQLite + Chroma 的现有组合，不迁移。** 同时为 SQLite 补齐并发参数：
`journal_mode=WAL`、`busy_timeout=5000`、`synchronous=NORMAL`，并在引擎上启用 `pool_pre_ping`。

## 理由

1. **目标场景是单机演示/个人项目**：SQLite 零部署、单文件、随项目走，克隆下来就能跑。
   换成 PostgreSQL 会让「快速开始」从三步变成「装库 + 建库 + 配连接串」。
2. **并发压力在写侧而非读写混合**：WAL 模式 + busy_timeout 足以覆盖本项目
   「多个用户同时提问、少量写会话」的负载特征。
3. **向量与业务数据分离存储**：Chroma 自带持久化，检索能力够用；
   pgvector 的优势（与业务数据同库事务）在本项目没有对应的需求。

## 后果

- 优点：部署简单、零外部依赖、演示与 CI 都轻量。
- 代价与已知限制（**已在 README 如实标注**）：
  - SQLite 不适合高并发写入；
  - **本项目没有引入 Alembic**，因此 ORM 模型加字段属于 schema 变更，需要**删除本地库文件重建**
    （开发期数据可重灌）。这是刻意的取舍：为一个演示项目引入迁移框架的成本大于收益。
